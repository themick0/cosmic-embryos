# Cosmic Embryos — harness

Before working here, read the repository's `AGENTS.md` and the mandatory
[competition operating rules](prompts/competition.md). The latter is included
in every production task template's initial prompt and frozen evidence, because
Codex runs intentionally disable AGENTS.md loading. It distinguishes maintainer,
locked researcher, and submission operator responsibilities, including the shared
T2 quota and the absence of a local quota reservation.

Infrastructure for autonomous Codex CLI runs in the Virtual Embryo Challenge.
All configuration, prompts, panels, logs, tests, and archives live under `ai/`.
Source measurements remain in `datasets/`. No biological model is implemented
here yet: the agent writes and selects one during a run.

All authored comments, docstrings, documentation, and reports must be in English,
including files generated by the agent. See the repository's `AGENTS.md`.

Repository-maintenance agents can use the local
[CodeGraph MCP integration](mcp/codegraph/README.md) for source navigation.
Its index covers `ai/` and excludes runtime artifacts and credentials. Locked
research runs explicitly disable this shared MCP server.

## Installation and checks

Requires Python 3.11+, `uv`, `curl`, Codex CLI, and macOS/Linux. Tested with Codex
CLI 0.163.0. Older versions without `--ignore-user-config` / `--ignore-rules` are
unsupported. Configure Codex authentication beforehand; `doctor` does not call
the model or check access to a specific model.

Run all commands below from the repository root:

```bash
uv sync --project ai --locked
uv run --project ai python ai/harness.py doctor
uv run --project ai python ai/harness.py inventory
uv run --project ai python -m unittest discover -s ai/tests -v
```

`ai/.venv` contains the harness dependencies: AnnData, HDF5, NumPy, HTTPX, and their
dependencies. A solution may also need scikit-learn, PyTorch, veckit, or other
libraries. Prepare the required environment **before prepare**. With networking
disabled, the agent can only use installed software and the local cache.
`context.json` contains the harness Python path; training may use a separate,
preinstalled environment described in the prompt before the run is locked.
The agent must record all library versions used and reproduction commands.

## Configuration

- `configs/t1.json`: RNA, E10.5 validation.
- `configs/t2.json`: three validation boards — embryo interpolation, heart
  interpolation, and heart extrapolation. All three share the budget.
- `configs/t3.json`: Gata4 knockout validation; uses the downloaded
  `datasets/E9.5_mab21l2_ko.h5ad`.

These are P2 templates as of October 18, 2026, **not final test configurations**.
For the October 20 release, refresh the published panels, add permitted validation
inputs, update `boards`/`targets`/prompts, and create a new run. Future test board
names have not been guessed or hardcoded.

Each template explicitly uses `gpt-6-astra` with `reasoning_effort: high`.
Override the exact model ID through `--model` or the configuration before a new
run. The harness never substitutes a model. The selected model must support the
configured reasoning effort. Check access and sandbox shell execution with a
small real call (this consumes model usage):

```bash
uv run --project ai python ai/harness.py codex-check --model gpt-6-astra
```

Its prompt, command, raw trace, and result are retained under `ai/checks/`.
For personal variants, copy a template to `ai/configs/t1.local.json`. These files
are excluded from Git, but the effective configuration is included in evidence.

Settings: `inputs` lists permitted measurements; `prompt_files` orders the
instructions; `boards` and `targets` specify required predictions;
`wall_time_seconds` sets the total Codex process budget, including training;
`seed` specifies the algorithm seed; `network_access` and `sandbox` control
permissions. The templates use `workspace-write` with networking and web search
disabled. They do not authorise external measured data. Research runs never
submit automatically; the separate `submit` command handles official uploads.

Every configuration, including local variants, must begin `prompt_files` with
`ai/prompts/competition.md`, then `ai/prompts/common.md`, followed by at least one
task prompt. Validation rejects missing or reordered shared instructions before
creating a run or probing Codex. Existing frozen runs remain unchanged.

Gene panels come from the official source. Their provenance and SHA-256 hashes
are recorded in `resources/panels/provenance.json`. Refresh them explicitly:

```bash
python3 ai/harness.py sync-panels
```

Refreshing does not change frozen copies in existing runs. It may make an
already prepared, unexecuted snapshot differ from the current source files;
prepare a new run in that case.

## Running

Prepare using the model already selected in the configuration:

```bash
uv run --project ai python ai/harness.py prepare \
  --config ai/configs/t1.json
```

This command does not call the model. It checks the configuration and CLI,
computes full input SHA-256 hashes, copies the harness/prompts/panels, and prints
`run_directory`. Hashing large inputs takes time. Inspect the snapshot and
command before execution. To make changes, edit the sources and create a **new**
snapshot; do not edit an existing snapshot.

Replace `RUN_DIRECTORY` with the printed directory:

```bash
uv run --project ai python ai/harness.py execute RUN_DIRECTORY
uv run --project ai python ai/harness.py status RUN_DIRECTORY
uv run --project ai python ai/harness.py verify RUN_DIRECTORY
uv run --project ai python ai/harness.py bundle RUN_DIRECTORY
```

Alternatively, prepare and execute in one command:

```bash
uv run --project ai python ai/harness.py run \
  --config ai/configs/t1.json
```

`execute` establishes the configuration lock, recorded in `started.json`.
From that point, the agent selects experiments and final files autonomously.
Do not steer its work based on intermediate results. The harness does not request
human input or provide a command for sending another prompt. The initial prompt
and Codex output are preserved exactly as accepted/emitted by the CLI. Hidden
internal model reasoning is not recorded.

Each run directory can execute only once. Re-execution is forbidden even after
failure, to preserve evidence. This version has no resume support: create a new
run after a failure and retain the old one. Ctrl-C, SIGTERM, CLI errors, invalid
outputs, or timeouts preserve logs but do not produce a successful competition
bundle. SIGKILL or power loss may leave status `running`; that directory also
cannot be reused or bundled as a successful run.

## Saved artifacts

```text
ai/
  harness.py                 # CLI
  embryo_harness/            # Configuration, Codex, validation, packaging
  configs/                   # T1–T3 templates
  prompts/                   # Shared prompt and task instructions
  resources/panels/           # Official board requirements
  tests/                     # Tests with a local Codex simulator
  .env.local                 # Local API key; excluded from Git and snapshots
  checks/                    # Real Codex smoke checks; excluded from Git
  submissions/<id>/          # Durable API requests and responses; excluded from Git
  runs/<id>/                 # Excluded from Git
    lock.json / lock.sha256   # Inputs, model, budget, versions, hashes
    started.json             # Start time and configuration lock
    frozen/                  # Harness, prompt, and panel snapshot
    work/                    # Agent code, experiments, and results
    trajectory.jsonl         # Raw codex exec --json event stream
    stderr.log               # CLI diagnostics
    final.json               # Agent's final selection
    validation.json          # Format checks and observed usage
    receipt.json             # Log and final artifact hashes
    status.json
  exports/<id>/              # Excluded from Git
    trajectory.tar.gz
    prompts.tar.gz
    harness.tar.gz
    prediction-1.h5ad
    manifest.json
    manifest.sha256
```

The agent returns JSON matching `frozen/final.schema.json`: selected predictions,
a method report path, a JSON list of external sources, and reproduction files.
The harness validates every declared artifact and records its SHA-256 hash.
`bundle` checks integrity again and copies selected predictions without
transformations. Replacing files, editing them manually, or reordering genes
after completion causes verification to fail.

Completed runs require both `receipt.json` and `receipt.sha256`: deleting either
is treated as evidence corruption. Verification also checks the exact file list
in `frozen/`; additions after locking are rejected. Before locking, input `.h5ad`
files are checked for self-contained storage: data cannot live in an external
file whose contents are not covered by the input hash.

The three archives correspond to trajectory, prompts, and harness evidence.
The harness archive includes solution code and agent-declared reproduction files.
All panels and individual prompts listed in the lock are also included.
Each prediction in `manifest.json` has a `run_path`, its original path inside the
run directory. After extracting the archives and placing predictions at those
paths, verify all frozen and output file hashes without the original datasets
using `core.verify(restored_directory, inputs=False)`. This verifies evidence;
retraining still requires the original datasets.
Source datasets, Codex authentication keys, and virtual environments are not
explicitly copied into the bundle. Agent commands can print sensitive information
into logs: prepare an environment with only the access required for the task.
Evidence is archived in full; exceeding 200 MB per archive fails without
truncation. The 600 MB limit applies **to the entire team**, while the harness
only knows the current bundle. Account for that quota before uploading evidence
from intermediate runs.

## Prediction validation

```bash
uv run --project ai python ai/harness.py validate path/to/prediction.h5ad \
  --board T1:val
```

Checks cover dense/CSR/CSC matrices, gene names and order, cell counts, finite
values, float32 representability, non-negative expression, sparse index structure,
and required 3D coordinates. Expression is read in blocks without densifying the
entire RNA matrix. Validation does not modify the file, calculate a biological
score, or replace the server's format check.
Structural readability is checked with real AnnData in `backed="r"` mode:
ordinary and nullable string indexes are supported, and annotations and auxiliary
arrays are checked. The main `.X` stays on disk, but AnnData loads annotations,
additional layers, and other auxiliary arrays into memory.
Before reading contents, the entire HDF5 graph is checked: external links,
virtual datasets (VDS), and external raw storage are forbidden, including nested
annotations and sparse matrix components. Internal links are allowed. The `.X`
encoding type and version are checked separately: `array/0.2.0`,
`csr_matrix/0.1.0`, and `csc_matrix/0.1.0` are supported. Legacy dense arrays may
omit both encoding attributes.
The root encoding must be `anndata/0.1.0`. Sparse values are also checked after
summing duplicate indices, using bounded chunks and one dense row/column at a
time, to catch overflow that would occur when the scorer densifies them.
For metrics, preinstall the official `veckit` package and include instructions
for using it in the prompt; it does not provide hidden targets.

## Competition API and submissions

The API client runs outside the locked agent process. Set `VE_CHALLENGE_API_KEY`
in the invoking environment, or create `ai/.env.local` containing one assignment:

```dotenv
VE_CHALLENGE_API_KEY=YOUR_PERSONAL_KEY
```

Replace the placeholder with a key created on the competition's API keys page.
The environment takes precedence. The local file supports blank lines, comment
lines, and an optionally quoted value; it is parsed as data, never executed as
shell code. Keep its permissions private (`chmod 600 ai/.env.local`). It is
excluded from Git, source snapshots, and evidence archives. The key is removed
from the Codex subprocess environment. This does not provide filesystem read
isolation: as with other credentials, do not instruct the agent to read the file.
No key is needed for public phase and board checks:

```bash
uv run --project ai python ai/harness.py api-check --public-only
uv run --project ai python ai/harness.py api-check
```

The authenticated check reads account state, stale consents, and team quotas.
Accept any outstanding Rules/Terms in the portal. Creating keys and accepting
agreements require your browser sign-in and are not performed by this client.
API requests use the official HTTPS origin; redirects are not followed.

After an agent run completes, verify and bundle it as shown above. Replace
`BUNDLE_DIRECTORY` below with its directory under `ai/exports/`:

```bash
uv run --project ai python ai/harness.py format-check BUNDLE_DIRECTORY --board T1:val
```

This uploads the selected prediction with `format_only=true`, without an
idempotency key or an official submission. Its response and prediction hash are
saved under `ai/submissions/`. Passing does not guarantee scorer acceptance.

The following command **creates an official submission and spends the applicable
competition allowance**. Invoke it only for a completed run you have chosen:

```bash
uv run --project ai python ai/harness.py submit BUNDLE_DIRECTORY \
  --board T1:val --method "My prediction method"
```

Use `--architecture "Shared architecture name"` when applicable, consistently
across related entries. The prediction method name is separate from the agent
model. Agent framework/model fields come from the bundle and locked run; T2
setting/mode come from the frozen board contract. Submit each selected T2 board
separately. Evidence is attached to each prediction's own submission ID.

Before a new official request, the client checks the live phase/board, registration,
Agent Team track, Cosmic Embryos team membership, and stale consents, reads the
current quota, and performs a server format check. The server
enforces remaining allowance, recovery credits, and concurrent team usage.
Current policy is eight scored submissions per task/UTC day in P2, shared by
the three T2 validation boards. P3 uses two official attempts per board across
the whole phase. The live API remains authoritative.

The command saves a stable `Idempotency-Key`, file hash/name, exact form fields,
bundle identity, and account binding (`team_id` and track) before the official
request. Resuming with another team's key is rejected before uploads; rotating
a key within the same team remains supported. Registration, team binding and
track are checked on resume and before each official POST attempt. Older state
without an account binding requires inspection of the original account before
recovery; never delete it or silently adopt the current key's team.
The command checks the server's returned
board and SHA-256, retains rejection responses even with HTTP 200, and attaches
all three evidence archives using the current evidence endpoint requirements.
The current gate requires at least two distinct kinds including trajectory;
prize verification needs all three. Evidence limits also apply across your team,
not just the current bundle, and the server enforces the remaining storage quota.

Retry a failed `submit` with the **same command and unchanged files**. Prediction
timeouts/5xx use exponential backoff and the same request identity. Before every
official POST, including automatic retries, the client checks that the original
phase and board remain active. If the phase changes, submissions close, or an old
uncertain request has no saved phase, it stops: preserve the request ID and inspect
submission history to recover any existing submission ID. A confirmed submission
can still finish attaching evidence after its phase closes. The API offers no
atomic expected-phase condition, so a transition between the check and POST
remains possible; returned board and hash checks still apply. HTTP 4xx responses
require resolving the reported problem. Evidence POSTs have no
idempotency support: the client reconciles their SHA-256 or content-addressed
note against the remote list before continuing after a lost response. An explicit
server digest takes precedence over the note. Matching kinds or a local success
record cannot establish file identity. The final remote scan must confirm all
three archive identities. The client also reads submission detail and recent
history before evidence uploads and after completion, checking `reclaimed_at`
where the API exposes it. It reports success only when the current status is
`queued`, `scoring`, or `scored`. History covers the latest 200 submissions;
absence from that list alone does not prove deletion. If the server cannot
establish whether an upload arrived, the client stops for inspection instead of
duplicating it. Do not delete submission state to force a retry.

An evidence response with a nonempty server `note` stops processing for inspection
and is retained in state. The documented reclaimed-prediction warning can arrive
with HTTP 200. A saved note also blocks automatic resume until it has been
investigated. A reclaimed prediction needs a separate authorised submission; the
client never creates a replacement automatically. `queued=false` alone is not an
error because a prediction may already be queued or scored. If the final status
still says `awaiting_evidence`, the command reports unconfirmed readiness; inspect
the saved response and resume the same command without duplicating archives.

Read status or poll every 20 seconds for a bounded period:

```bash
uv run --project ai python ai/harness.py submission-status RUN_ID --board T1:val
uv run --project ai python ai/harness.py submission-status RUN_ID --board T1:val --wait-seconds 300
```

Each status poll reads both submission detail and recent history. A confirmed
`reclaimed_at` is saved and immediately ends polling; the returned JSON includes
`polling_stopped: "prediction_reclaimed"` while preserving the server's status.
Previously confirmed reclamation remains recorded if the entry later leaves
the latest-200 history window. A missing history entry alone does not indicate
deletion. Ordinary terminal statuses, including rejections, are returned without
further waiting. Status checks never create replacement submissions.

Requests and responses live in `ai/submissions/<run_id>/`. A process lock prevents
concurrent commands from creating competing requests for the same run/board.
The evidence bundle stays unchanged after upload; local submission state records
the submission ID, evidence progress, and server status. A phase change requires
new research configurations and runs; the client rejects obsolete boards for
new uploads and never relabels validation predictions as test predictions.

## Limits of the guarantees

- Time is limited by a process timeout and termination of its process group.
  This does not impose GPU/RAM/disk quotas or cost/token limits. Usage comes from
  completed Codex events and may be incomplete after failure. Detached processes
  and external compute jobs require limits enforced by the environment.
- SHA-256 detects changes but is not independent attestation: the machine owner
  can rewrite both files and hashes. Organiser review remains necessary; the
  harness does not guarantee that evidence will be accepted.
- The CLI runs with user configuration and AGENTS.md loading disabled, explicit
  model/access flags, and no interactive approvals. The shared prompt includes
  the repository's English-language requirement for generated content.
  Authentication, system software, infrastructure policies, and the process
  environment remain external. This is not a hermetic container. The CLI version,
  entrypoint hash, Python, installed Python packages, and PATH are recorded;
  a complete OS image and all system binaries are not archived. Pin the compute
  environment image before execution when strict reproducibility is required.
- Allowed sources are specified by the prompt and manifest. `workspace-write`
  restricts writes but does not itself prevent reading other machine files.
  For technical data isolation, use a separate environment containing only
  permitted datasets. Hash checks detect input changes after execution but do
  not physically prevent them.
- Enable `danger-full-access` only as a deliberate configuration choice before
  a new run; this mode cannot enforce network denial. If the environment does
  not support the sandbox, the failure is recorded without automatically
  weakening the mode.
